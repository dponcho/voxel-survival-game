## Implemented runtime boundary

`OperationMetrics` v2 retains the original upload/deletion records and adds
inclusive completed-task application spans. The enclosing application span can
contain child upload/deletion hooks. The synchronous terrain charge is
`upload + deletion + application - application_nested`; each interval is charged
once. The inclusive application maximum is independently checked against 750 µs.
No OS CPU-service, GPU or renderer-deferred attribution is inferred from it.

Native-frame totals survive phase closure, report-writer gaps and subsequent phase
beginnings. Only `begin_frame` resets them. If limits change in a native frame,
the strictest allowance used by its work remains authoritative. The v2 CSV adds
ten columns to the original eighteen; legacy records remain readable as partial
evidence. Phase maxima, lifetime deltas, complete rows and native-frame carry
are independently reconciled. An idle tail can retain an earlier same-frame
overrun; it is labelled a whole-frame failure, not new work in that tail.

Completed-task admission now reserves 750 µs before starting another
non-preemptible application, as uploads already did. The reserve cannot guarantee
an operation meets that bound; actual exceedances remain failed evidence.
Largest individual payload is recorded independently of the slowest operation's
payload. The normal/heavy 1/2 ms, 512 KiB/1 MiB and individual 256 KiB limits
are enforced separately. Native caps and world/save semantics are unchanged.

`m1_ordinary_admission_runtime.gd` uses the actual production main/physics paths,
including the outward route and camera reversal at tick 900. It adds no mesh
resource snapshots or admission output. The optional priority policy is applied
only during gameplay/acknowledgement, with FIFO during preparation/retirement.
The ordinary frontier, edit, operation and complete-callback ledgers remain.
Selection/resource observations are unavailable/null, never fabricated zeros.
Its report distinguishes evidence integrity from bounded acceptance, timing
assessment and target qualification. Ordinary production remains FIFO until an
explicit adoption decision has relevant regression and target evidence.

## Prospective diagnostic policy adopted by this review

This section records the adopted v1 elapsed method and its original stop rule.
After its inconclusive cloud pilot, the October 17
[v2 measurement decision](M1_DIAGNOSTIC_COST_POLICY.md) prospectively replaces the
cost estimand with whole-process CPU-cycle demand. Its implementation is pending;
the v1 evidence and verdicts below are unchanged.

The below-1% requirement applies to optional diagnostics enabled during ordinary
shipping gameplay. Required collision/readiness, admission limits, transaction
integrity and other operational safeguards remain active in both controls.
Budget clocks needed to enforce those safeguards are operational work, not
optional diagnostics that can be removed to manufacture a faster comparison.

Expensive forensic traces run in an explicitly separate diagnostic configuration.
Their cost is disclosed, and their wall times cannot certify ordinary-play frame
performance. A companion forensic run may establish correctness only with exact
binary identity and matched gameplay/configuration/work evidence. It does not
substitute for observing a critical unobservable behavior in the shipping path.
The complete ordinary and forensic configuration inventories must be committed
before a target qualification candidate is selected. They do not yet exist as
complete shipping runtime modes; this policy is not a claimed implementation or
measurement result.

Adopt one prospective method: matched fixed-work complete-trial elapsed duration,
with repeat comparisons at matching route positions and callback count reported
separately. Different sections of one route need not cost the same. Native closure,
last-edit acknowledgement, optional diagnostic setup, writer drain and final
report work are separately bracketed and included in the declared total boundary;
overlapping intervals are never added. Preparation/retirement remain explicitly
scoped, with their work retained. Common external qualification-observer costs and
any excluded operational work must be listed; the estimand is the incremental
effect of the declared shipping diagnostic inventory, not an unmeasured total.

Before any full target matrix, predeclare a single focused pilot: one matched null
quartet and one known-positive quartet, same route/work, with a separately recorded
above-limit 2% positive cost. Fixed work, complete duration, count decomposition,
matching-section repeat drift, I/O and genuine workload/operation failures remain
guards. Use a conservative range of complete-trial repeat effects; it is not a
statistical confidence interval. A pass needs valid sensitivity controls and an
upper effect bound below 1%. An above-limit lower bound fails. A range crossing
1%, negative attribution, failed controls or unresolved drift is inconclusive.
Do not waive terminal uncertainty or quietly replace the hardware pilot with
synthetic clocks. The pilot's exact injection/observer implementation and boundary
must be reviewed before execution. No target run is requested by this commit.

If that pilot is inconclusive, stop calibration work and record the resolution
limit and a concrete policy choice (supported measurement change, more declared
repetitions, or an explicit threshold decision). Do not start another calibration
branch by default. The current `diagnostic_ab` outputs and all historical reports
remain unchanged and readable; the known flatness classifier is a legacy
assessment, not the prospective shipping qualification method. The successor
shipping overhead gate is `not_run`, with qualification false.
